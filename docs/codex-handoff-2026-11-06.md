# 交给 Codex：Mac 端两个问题的修复方案（2026-11-06）

代码都在 `macos/`，构建和测试命令见 `macos/README.md`。macOS 测试 target 是 `WakeOnCueTests`，纯逻辑测试放在这里。两个问题彼此独立，可以分成两个 PR，每个都开 PR、不要合并。

不要替换 `/Applications/WakeOnCue.app`，也不要用 Debug 版直接打开正式数据：Debug 版和正式版共用同一个数据库和偏好设置。需要真实数据时，用 `WAKEONCUE_DATA_DIR` 指向一份副本（`sqlite3 … ".backup"` 导出数据库，再复制 `Audio/`），重放方法见 `App/DebugSnapshot.swift` 里的 `replay` 命令和 `AppModel.replayOnly`。

## 问题 1：Qwen 逐句重转失败或中断后，不会再补

### 现象

- 正常运行时影响很小：11-05 14:54 到 11-06 09:45 共 2045 句麦克风句子，只有 5 句超过 2.5 秒却没被重转（`refined_by IS NULL`）。
- App 被杀或重启后会漏一大批：11-05 15:34 系统内存不足杀掉了 App，重放副本里当时排队的约 2274 句再也没被重转。对整天点「重新转录」后，11-04 的 11 点仍有 139/174 句、15 点有 168/270 句没被重转，手动再触发一次才降到 27 句和 25 句。
- 这些句子留着 Apple 的实时文字：没有标点、错字多，总结和搜索的质量都受影响。

### 原因（`Transcription/Refiner.swift`）

1. 待重转的队列 `queue` 只在内存里。App 退出、崩溃或被杀时，排着队的实时句子全部丢失，之后没有任何机制补回来。
2. `use(_:service:)` 每次重新选择或加载模型（包括每次启动）都会执行 `queue.removeAll { $0.batch == nil }`，把还没处理的实时句子直接扔掉。
3. `drain()` 里，如果 `recognizer == nil` 而状态不是 `.loading`（比如模型加载失败），实时句子出队后既不处理也不放回，直接丢掉。
4. `refine()` 在 `recognizer.recognize` 抛错、或者读不到足够的音频（`samples.count <= 1_600`）时返回 `nil`，不记录，也不重试。

### 方案

把「还没重转」改成数据库里查得到的状态，再用后台巡检来补，不再依赖内存队列：

1. **数据库**（`Storage/Store.swift`，按现有方式加迁移）：`sentence` 表加三列：
   - `refine_attempts INTEGER NOT NULL DEFAULT 0`
   - `refine_next REAL`：下次可以重试的时间
   - `refine_checked_by TEXT`：已经用哪个模型检查过、但决定保留实时文字（`TranscriptFilter.shouldReplace` 返回 false）。
2. **需要重转的条件：**
   - 句子不在私人或已删除的时段里；
   - `refined_by` 为空；
   - `refine_checked_by` 不等于当前模型名；
   - `refine_attempts < 4`；
   - `refine_next` 为空或已经过了；
   - 句子在 7 天以内，且结束超过 8 秒；
   - 当前选了模型或转录服务。

   在 `Store` 里写一个查询，按时间从早到晚返回前 N 句。
3. **巡检：** 下面这些时机各跑一次，把查到的句子放进队列（跳过已在队列里的，用一个 `Set<Int64>` 记录）：
   - 模型加载成功后（`use()` 里 `status = .ready` 之后）；
   - App 启动后；
   - 之后每 5 分钟一次。
4. **失败处理：** `refine()` 失败时（抛错、音频不够），把 `refine_attempts` 加 1，`refine_next` 按 1 分钟、10 分钟、1 小时退避。决定保留实时文字时，写 `refine_checked_by = 当前模型名`。成功时按现有逻辑写 `refined_by`。
5. **不再丢任务：** 删掉 `use()` 里的 `queue.removeAll { $0.batch == nil }`；`drain()` 在没有可用 recognizer 时停下等待，不再把实时句子出队丢掉。换模型后，`refine_checked_by` 不等于新模型的句子会被巡检重新挑出来，这就是想要的效果。
6. **「重新转录」批次：** 批次里失败的句子同样记次数，由巡检补。批次结束后，进度和要重新总结的小时沿用现有逻辑。被巡检补上的句子，如果文字变了，所在小时要重新总结：复用 `onHourRetranscribed`，按小时去重，同一小时 10 分钟内最多触发一次。
7. **体检命令**（`WakeOnCueCLI/Health.swift`）：每天加一行「还没重转：N 句（超过 2.5 秒的 M 句）」，只在当前选了模型时显示。

### 验收

- 单元测试：需要重转的查询（私人时段、已检查过、次数用完、退避未到都要排除）；退避时间的计算。
- 用副本做实际验证：重转进行中直接 `kill -9` Debug 版再打开，5 分钟内剩下的句子要自动补上。在 11-03/04 的副本上，「重新转录整天」之后，超过 2.5 秒却没被重转的句子应少于 1%。
- 现有测试全部通过。

## 问题 2：飞书一直开着静音输出，会议那一路整夜都在录；自动学声纹因此学错

### 现象

- 11-05 14:52 到 11-06 09:45，会议那一路（来源「飞书」）录了 16.8 小时，夜里每小时都有 55–60 分钟。抽查的 5 段（包括傍晚和半夜）都是 -91 dB，也就是完全没有声音。这一路一句转录都没有。
- 浪费存储：按 32 kbps 算，每天大约 200 MB 以上的静音；时间线的音轨、体检里的「会议 App N 小时」也因此不对。
- **更严重的连带问题：** `Voices` 在没有录入声纹时，会把「会议 App 正在播放」期间麦克风里的话当成用户本人来学声纹（#25 的功能）。因为飞书一直被当成「在播放」，学进去的其实是房间里所有人的声音。钥匙串里已经有一份错误的 `me-learned`，之后又按它重判了最近 7 天：11-05 起出现了「说话人 250」这样的编号，大量用户自己的话被标成了他人。

### 原因

- `Capture/AudioDevices.swift` 用 `kAudioProcessPropertyIsRunningOutput` 判断进程「在播放」。飞书（`com.bytedance.macos.feishu`）一直开着输出，即使输出的全是零，这个属性也是真。
- `Capture/Recorder.swift` 的 `refreshMeetingAudio()` 只要属性为真就接上 tap，`ChannelPipeline` 收到什么就写什么，不看有没有声音。`activeMeetingApps` 因此一整天都不是空的。
- `Transcription/Voices.swift` 的 `enqueue` 用 `!recorder.activeMeetingApps.isEmpty` 判断「在开会」，并据此学声纹（`learn`）。

### 方案

1. **按实际声音写盘**（`Capture/ChannelPipeline.swift`，只对会议这一路，麦克风不变）：
   - 每个 buffer 算峰值，低于 -70 dBFS 算静音。
   - 没有声音时不开分段文件；第一次有声音时打开，并带上前面约 2 秒的预录（环形缓冲）。
   - 连续静音 60 秒后关闭分段。
   - 静音的 buffer 不发给转录（`onAudio`）。
   - 继续按 5 分钟对齐切段，时间线保持准确。
2. **「正在播放」改成「最近真的有声音」**（`Recorder`）：tap 照常接（开销小），但 `activeMeetingApps` 只列出最近 90 秒内这一路有过声音（超过 -70 dBFS）的 App。菜单栏、设置页、状态文字都会跟着变对。
3. **自动学声纹加三道保护**（`Voices`）：
   - 「在开会」的判断改成：这句话的时间段里会议那一路有声音，**而且**前后 60 秒内会议那一路有转录出来的句子（真实的通话一定有对方在说话）。
   - 已经学了 5 句以上之后，新样本和当前均值的相似度低于 0.5 就丢弃，防止混进别人的声音。
   - 学到的声纹在启用前，和最近 7 天麦克风句子的相似度分布要有明显的一团（至少 20% 的句子 ≥ 0.5），否则不启用，并在日志里记一条。
4. **一次性修复已经学错的数据**（加一个版本号标记，只跑一次）：
   - 删掉钥匙串里的 `me-learned`。
   - 最近 7 天的麦克风句子，没有用户手动起名（`speaker_name` 为空，或者以「说话人 」开头）的，恢复成 `speaker = me`、`speaker_name = NULL`；按现有规则重新区分说话人（「区分说话人」开着时，只对「他人」聚类）；受影响的小时重新总结。
   - 删掉会议那一路里整段是数字静音（峰值低于 -70 dBFS）的旧分段文件和记录，`segment` 表里同步删除。只删会议那一路，不碰麦克风。
5. **说话人编号过多**（`Voices.cluster`）：远处录音同一个人两句的相似度中位数约 0.69，`clusterThreshold = 0.6` 会让很多句子各自成为新的说话人。改成：
   - 阈值降到 0.5；
   - 短于 2 秒的句子不新建说话人，只标「他人」；
   - 一天里只有 1–2 句的说话人，并入最相近的已有说话人，没有足够近的就改回「他人」。

### 验收

- 单元测试：静音判断和分段开关（静音不开文件；有声音时带上预录；60 秒静音后关闭）；`activeMeetingApps` 按声音判断；学声纹的三道保护；一次性修复只处理该处理的句子。
- 用副本做实际验证：在 11-05 14:52 到 11-06 09:45 的副本上重放会议那一路，静音段不再生成分段文件。修复跑完后，`me-learned` 被删掉，11-05 起的「说话人 N」编号不超过十几个。
- 在正式机器上开一场真实的飞书会议，对方的声音照常录进「会议对方」，会后几分钟内出会议要点。
- 现有测试全部通过。

### 用户现在可以先做的

设置 › 声音 › 学到的声音点「忘掉」。这样新的句子不再按错误的声纹判定，已经标错的句子等上面第 4 步来恢复。
